# Sandbox Identity and Transaction Verification Controls

## Implemented in this sandbox

- Six-digit PINs are scrypt-hashed before persistence.
- Incorrect PIN attempts increment a counter; five failures set a 15-minute lock.
- A new money-moving transfer requires a short-lived OTP challenge bound to the authenticated user and sandbox security session.
- OTPs expire after five minutes, are limited to five failed attempts, and are marked consumed in the same transaction that creates the transfer intent.
- Device and security-session records are user-scoped; revoke endpoints check ownership. Revoking a device revokes its associated security sessions.
- A PIN rotation requires the current PIN, rejects reuse of the current value, resets the failure counter on success, and revokes all other sandbox security sessions.
- The OTP consumption update requires the `verified` state, matching user/session, and a future expiry time, so concurrent reuse fails closed.
- A transfer is limited to **L 1,000.00** and each authenticated user has an atomic daily UTC sandbox intent reservation of **L 2,000.00**. The reservation rolls back with a failed transfer-creation transaction.
- The user security screen shows recent safe audit-event labels and the usage of the sandbox limit; no secret or raw identifier is exposed there.
- The UI maps backend transfer states to explicit `Verificando`, `Pendiente`, `Completado`, `Rechazado`, `Fallido`, `Expirado`, and `Cancelado` labels.

## Explicit sandbox limitations

- The OTP is returned to the UI **only to demonstrate the flow**; no email, SMS, push, or verified delivery channel exists.
- Device identifiers are generated by the client and are not proof of possession, hardware identity, or browser integrity.
- Security sessions gate the sandbox transfer-verification flow. They do **not** revoke the Manus OAuth session or implement full session rotation.
- PIN creation/update does not include recovery, verified identity re-check, or a full sensitive-change workflow.
- The transfer cap and UTC-day reservation are demonstration guardrails, not a production velocity, AML, fraud, or regulatory limit.
- No WebAuthn enrollment, KYC, biometric authentication, account takeover monitoring, device-risk scoring, or production incident response exists.

## Minimum production follow-up

1. Use a verified out-of-band OTP delivery provider with rate limits, delivery telemetry, and anti-enumeration behavior.
2. Bind device trust to WebAuthn/passkeys or another independently verifiable credential; do not trust a client-generated ID alone.
3. Implement first-class session tokens with rotation, revocation, timeout, secure cookie controls, and audit correlation.
4. Require step-up verification and recovery safeguards for PIN reset, trusted-device enrollment, and high-risk money movement.
5. Add database integration and adverse-path tests for cross-user ownership, concurrent challenge use, expiry, lockout, and session/device revocation.
